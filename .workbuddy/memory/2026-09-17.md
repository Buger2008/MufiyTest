# 2026-09-17

## MufiyApp1 的 NativeAOT 发布配置（win-x64 已跑通；win-x86 被 Mufiy 卡死）

### 做了什么
- 给 `MufiyApp1/MufiyApp1.csproj` 加了 AOT 条件块（`Condition="'$(PublishAot)' == 'true'"`），
  新增 `MufiyApp1/AotRoots.xml`（`@(TrimmerRootDescriptor)`），普通 build/调试完全不受影响。
- 发布命令：`dotnet publish MufiyApp1.csproj -c Release -f net11.0 -r win-x64 -p:PublishAot=true`
  （多目标工程必须 `-f net11.0`，否则 NETSDK1129）。
- 产物：`bin/Release/net11.0/win-x64/publish/`，8.9 MB 单 exe（COM RVA=0 纯原生）+ SDL3.dll /
  WebView2Loader.dll / libHarfBuzzSharp.dll / libSkiaSharp.dll，无托管 DLL。
  实测 win-x64 启动 646 ms，窗口 "Form1" 548x336 正常显示。

### 两个关键坑（结论都写进了 csproj / AotRoots.xml 注释）
1. **裁剪剪掉了反射构造的构造函数**
   `Mufiy.DefaultTheme` 用 `Activator.CreateInstance` 创建颜色表，AOT 的 TrimMode=full 把
   `Mufiy.WindowDecorationColors..ctor`（元数据里确实存在，Public RTSpecialName）当死代码剪掉 →
   运行时 `MissingMethodException: No parameterless constructor defined`。
   解法必须**按类型精确 root**（`IThemeColorTable` 的 37 个属性类型：`Mufiy.*ColorSet` +
   `Mufiy.WindowDecorationColors`）。
   **不能用 `@(TrimmerRootAssembly)` root 整个 Mufiy.dll**：会牵出混淆包里的坏 token，
   ILC 在 `CompilerGeneratedState` 阶段硬崩 `BadImageFormatException: The format of a DLL or
   executable being loaded is invalid`，连包都发不出来。`IlcScanReflection=false` 救不了。

2. **win-x86 目前不可能实现（Mufiy 自身缺陷，非 AOT / 非配置问题）**
   `Mufiy.Window..ctor()` 里 P/Invoke `SetWindowLongPtr`，该导出**只存在于 64 位 user32.dll**：
   System32\user32.dll 有 `SetWindowLongPtrA/W`，SysWOW64\user32.dll 只有 `SetWindowLongA/W`。
   对照实验证明与 AOT 无关：`-r win-x86 -p:PublishAot=false -p:SelfContained=true` 同样崩；
   Mufiy/Provider 升到 0.0.1-Beta9 同样崩。
   → 已告知用户：在 Mufiy 修好前请用 win-x64。

### 顺带发现
- nuget.mikoui.com 上 Mufiy 全系列（mufiy / mufiy.platform.desktop.provider /
  mufiy.resxmapgenerator.nodependencies / mufiy.xaml / mufiy.xaml.sourcegenerator）都有
  `0.0.1-beta9`，但本项目 csproj 里 Mufiy 钉的是 `0.0.1-Beta8`，其余是 `*-Beta*` 浮动值——
  实际 restore 解析出来仍是 Beta8（浮动值未重新求值）。
- Mufiy 发布包是**混淆**过的（类型名形如 `IqP5FkAaX9Xh020pnoF`、字段名形如 `DmWNYEwbJR`），
  内部 IL 有坏 token；且 obfuscation 让 `TrimmerRootAssembly` 这条路不可用。

## 追加：win-x86 已用手工入口点映射跑通（同日晚）

用户要求「帮我手工实现一个入口点映射32位的SetWindowLong」，已实现并**实测通过**。

### 最终方案：转发 DLL + `NativeLibrary.SetDllImportResolver`（不改动 NuGet 包）
新增/改动文件：
- `MufiyApp1/Native/user32.x86.def` —— 纯转发表源文件（含重新生成命令）
- `MufiyApp1/Native/mufiy.user32.x86.dll` —— 生成的 x86 转发 DLL（2560 字节，无代码）
- `MufiyApp1/Win32EntryPointShim.cs` —— `Register()` 里对 **Provider 程序集**注册 resolver，
  只接管 `user32.dll`，`IntPtr.Size != 4` 时直接 return（x64 零影响）
- `Program.cs` —— `Main()` 第一行调 `Win32EntryPointShim.Register()`
- csproj —— `Condition="'$(RuntimeIdentifier)' == 'win-x86'"` 的 ItemGroup 把 DLL 拷到输出
  （**必须写 `Link`**，否则会落到 `Native\` 子目录，运行时按程序目录找不到）

关键事实：
1. **NativeAOT 确实支持 `NativeLibrary.SetDllImportResolver`**（`ResolvePInvokeSlow` 会查 resolver）。
   这是整个方案的可行性前提，已实测。
2. resolver **只能重定向库名、改不了入口点名**，所以转发 DLL 必须补齐该程序集用到的
   **全部 15 个 user32 入口点**，否则重定向后其它 API 反而找不到。
3. 非 Ptr 的 13 个要按真实 user32 的 A/W 变体 1:1 转发（裸名 `SendMessage`/`CallWindowProc`/
   `GetWindowLong`/`SetWindowLong`/`PostMessage` 在 user32 里**不存在**，只有 A/W），
   这样「探测 W→A→裸名」的顺序与真实 user32 一致，行为零差异。
4. `SetWindowLongPtr` 声明是 `CharSetUnicode` 且未设 `ExactSpelling` → 运行时先探 `SetWindowLongPtrW`
   再探裸名，所以这两个名字都要导出。
5. 生成命令（link.exe 取 VS 的 `Hostx64\x86\` 那份）：
   `link.exe /dll /noentry /machine:x86 /def:user32.x86.def /out:mufiy.user32.x86.dll`

### 实测结果
- win-x86 AOT：窗口 `Form1` 548x336 **正常显示**，启动 565 ms，stderr 空；
  exe `machine=0x014c`、`COM_RVA=0`（纯原生），publish 目录 0 个托管 DLL。
- 之前失败的版本做对照，确认没有 shim 必崩（同样命令、只差 shim）。

### 附带修掉的一个独立问题
`Mufiy` 钉死 `0.0.1-Beta8`、其余三个写 `*-Beta*` 浮动。包源已发布 Beta9 后，
清掉 NuGet v3 http 缓存再还原 → 浮动项解析到 Beta9、与钉死的 Beta8 冲突 →
`NU1605 包降级错误`，**干净还原直接编不过**。
已把四个包统一钉到 `0.0.1-Beta8`（= 现有实际在用的版本，行为零变化）。
要升 Beta9 必须四个一起升；实测 Beta9 同样有 32 位 SetWindowLongPtr 缺陷。

## 追加：win-x86 产物在 Windows 7 上 0xc0000005 —— 是 .NET 的 OS 下限，不是本项目问题

### 结论
**Windows 7 跑不了**，且不可能靠配置/补丁解决：
- 官方支持矩阵：.NET 8/9/10 的 Windows 客户端下限是 **Windows 10 1607+**；
  「Support changes from .NET 6.0：Windows Client 7 SP1 / 8.1 从 .NET 7.0 起不再支持」。
  最后一个支持 Win7 的是 **.NET 6，已于 2024-11-12 EOL**。
- 本项目 TFM 是 `net11.0`，且 **Mufiy 包只有 `lib/net10.0`**（没有 net6/7/netstandard 版本），
  所以连「降目标框架」这条路都没有。
- `Mufiy` 包里的 `net10.0-windows7.0` 是 **Windows 7.0 API 版本号**（编译期 API 面），
  不代表能在 Win7 上运行——容易误读。

### 硬证据（导入表，dumpbin /imports）
- `MufiyApp1.exe`（AOT）静态导入 **`api-ms-win-core-synch-l1-2-0.dll` → `WaitOnAddress` /
  `WakeByAddressSingle` / `WakeByAddressAll`**。该 API 集是 **Windows 8 引入**的，Win7 上没有。
- `libSkiaSharp.dll` 导入 `d3d12.dll` + `D3DCOMPILER_47.dll`（Win10 组件）。
- `SDL3.dll` 导入 `VCRUNTIME140.dll` + 一堆 `api-ms-win-crt-*`（Win7 需另装 VC 运行时/UCRT）。
- **最小探针证明与 Mufiy / Skia / shim 无关**：1.09 MB 的纯 .NET 11 AOT x86 空程序
  （不引用任何第三方包）同样静态导入 `api-ms-win-core-synch-l1-2-0.dll`。
  探针已放在 `_diag/AotProbe-win-x86.exe`（本机 Win10 上跑通：写入 `probe-result.txt` + 弹框）。
  在 Win7 上如果它也是 0xc0000005 → 运行时层不通，整条路封死。

### 若必须支持 Win7 的可行路径
1. 目标机升到 Win10 1607+（唯一能让现有这套 Mufiy + .NET 11 跑起来的路）。
2. 换栈：**.NET Framework 4.8 + 官方 WinForms** —— 官方支持 Win7 SP1 的组合；
   但 Mufiy 用不了（只有 net10.0），且 .NET Framework 不支持 NativeAOT。
3. 社区 hack（VxKex / One-Core-API 把 Win8/10 API 搬到 Win7）：不可交付，仅自用试验。

## Win7 上的 BEX / 0xC0000409（异常偏移 0x219865）
- `0xC0000409` = STATUS_STACK_BUFFER_OVERRUN，但**不等于栈溢出**：它是通用 fast-fail 码，
  WER 归类成 BEX。**NativeAOT 里未处理的托管异常就是走 fail-fast 变成 0xC0000409** —— 所以
  「BEX」的真相往往是「某个异常没人接」，先别往内存破坏方向查。
- 用 PDB 反查异常偏移（`_diag/resolve_rva.py`，dbghelp `SymLoadModuleEx`+`SymFromAddr`）得到：
  `S_P_CoreLib_System_Runtime_CompilerServices_ClassConstructorRunner__EnsureClassConstructorRun`
  @ `ClassConstructorRunner.cs:99` —— 那一行正是 `catch (Exception e)` 里的 `throw wrappedException`，
  **即某个静态构造函数抛了异常**。
- 对策：新增 `StartupDiagnostics.cs`（WinExe 无控制台，只能落 `startup-diagnostic.log`），
  写运行时时序/关键原生库可用性/每个启动阶段/未处理异常全链；`Program.cs` 的链式构建拆成逐句加 stage。
  等用户在 Win7 上跑一次把日志发回来，即可定位到具体的 cctor 与异常类型。

### Win7 实测结果（用户回传日志）与最终根因
日志（Win7 6.1.7601 x86）显示：`stage: MufiyApp.Run` 全部走完，
`!! System.NullReferenceException` 抛在
`Mufiy.RenderingBackend.Skia.SkiaBackend.CreatePopWindowGraphics → GetGRContext()`。
即 **TFM + InvariantGlobalization 已把加载期与 cctor 问题解决**，剩下的是纯渲染问题。

根因链条：
1. `probe d3d12.dll = 不可用` / `D3DCOMPILER_47.dll = 不可用`（Win7 本来就没有 d3d12）。
2. 模板 `Program.cs` 写的是 `option.GpuBackend = GpuBackendType.OpenGL`，
   但**在 Windows 上 Mufiy 的 Skia 后端实际走 D3D12**（Win10 上枚举进程模块可见
   d3d12.dll + D3D12Core.dll + D3DCOMPILER_47.dll + DXGI）。
3. Win7 上 GRContext 创建失败 → 返回 null → `GetGRContext()` 解引用 → NRE → 未处理 → fail-fast 0xC0000409。
4. **`MufiyAppConfig.GpuBackend` 的文档默认值就是 `Software`**（"Gpu后端(Default: Software)"），
   模板把它覆盖成 OpenGL 才是问题源头。

已改为 `option.GpuBackend = GpuBackendType.Software;`（回到 Mufiy 默认）。
本机（Win10）复验：窗口正常、截图有 212 种颜色 / 95.2% 非背景像素（真在渲染），
且 `D3D12Core.dll` 不再被加载（= 没创建 D3D12 设备）。**待 Win7 复测。**

**→ 最终结论（用户 Win7 实测）：通过，运行流畅不卡。**
所以 win-x86 在 Win7 上可行的完整条件 = `net10.0` + `InvariantGlobalization=true`
+ `GpuBackend=Software` + 32 位 user32 入口点 shim（+ 目标机有 UCRT）。
用户不必开 `SoftwareDisablesAnimation`（实测不卡，就没动它）。

### 走过的弯路（别再踩）
- 想用「在程序目录放一个同名空壳 `d3d12.dll`」来本机模拟 Win7 缺库 —— **不成立**：
  `NativeLibrary.TryLoad("d3d12.dll")` 会因为空壳存在返回 true，程序被引到另一条分支，
  表现和真缺库完全不同。
- 模块清单只能作弱证据：`d3d12.dll` / `D3DCOMPILER_47.dll` 可能被 SDL3 的视频驱动探测加载，
  不代表 Skia 真的建了 GPU 上下文；`D3D12Core.dll` 才是"建了 D3D12 设备"的强信号。
- 「出了窗口」≠「渲染了」。用 `_diag/check_render.py` 抓窗口像素统计颜色分布才算数。
- 备选方案 D3D12on7（微软官方 `Microsoft.Direct3D.D3D12On7` 含 d3d12.dll + dxilconv7.dll）：
  微软要求应用显式从 `12on7\` 子目录加载，且它依赖 Win8.1+ 的 DXGI（`CreateDXGIFactory2`），
  社区要靠额外的 `dxgi.dll` 包装才能让 D3D12 游戏在 Win7 跑。Skia 的后端不是按 D3D12on7 规范写的，
  风险高，暂不采用。

## Linux 构建踩坑：`NuGet.targets(200,5): error Root element is missing`

用户在 Linux 上 `dotnet publish ... -r linux-x64 -p:PublishAot=true` 时撞到。已定位：
**死机把 `.nuspec`（以及其他 XML 生成物）只写了一半**，`~/.nuget/packages/<id>/<ver>/<id>.nuspec`
是 0 字节或被截断 → NuGet 按 XML 解析时报 `XmlException: Root element is missing`。

要点（下次直接用）：
- 还原路径上被当 XML 读的只有三类：包里的 `*.nuspec`、`nuget.config`、`obj/*.nuget.g.props|targets`。
  硬关机/死机之后这三类都可能是半截的，**要一起清**，只清包缓存不够。
- 定位：`find ~/.nuget/packages -name "*.nuspec" -size 0 -printf '%h\n' | sort -u`
- 修复顺序：删坏包目录 → `dotnet nuget locals http-cache --clear`（防半截 `.nupkg` 被复用）
  → `rm -rf MufiyApp1/obj MufiyApp1/bin` → `dotnet restore`。
- **跨系统别复用 `obj/`、`bin/`**：里面的 `*.nuget.g.props|targets` / `project.assets.json`
  写死了 Windows 路径与 RID 解析结果。从 Windows 拷工程到 Linux 前先删掉。







## macOS 的 NativeAOT 构建 + 自动发布（GitHub Actions）

新增 `.github/workflows/build-macos-aot.yml`（手动触发），产出 `MufiyApp1-<ver>-macos-arm64.tar.gz`
与 `-macos-x64.tar.gz`，两个 tar 自动挂到一个 GitHub Release（附 SHA256SUMS）。

关键结论（都已核对到具体源码/文档）：
- **NativeAOT 不能跨架构/跨 OS 交叉编译** → 必须 arm64 用 arm64 runner。
  runner 标签（2026-09 现状）：`macos-15`（Apple Silicon）/ `macos-15-intel`（Intel）。
  `macos-13` 已于 2025-12-04 退役；`macos-latest`/`macos-14`/`macos-15`/`macos-26` 全是 arm64。
- **rpath 是 macOS 上能不能起来的关键**。NativeAOT 只给"聚合 shim"加
  `-Wl,-rpath,@executable_path`，主可执行文件不加；而 libSkiaSharp / libHarfBuzzSharp / libSDL3
  的 install_name 都是 `@rpath/xxx.dylib` → 不补 rpath 就是
  `dyld: Library not loaded: @rpath/libSkiaSharp.dylib`。
  已在本工程 csproj 里加（仅 OSX + PublishAot 生效）：
  `<ExtraLinkerArg Include="-rpath,@executable_path" />`（ExtraLinkerArg 会被包成 -Wl,<值>）。
- **`.NET 10 的 ILCompiler 只在 Xcode 15 上加 `-ld_classic`**（本机 ILCompiler 10.0.11 实测确认），
  Xcode 16/26 不涉及；要绕开用 `-p:UseLdClassicXCodeLinker=false`。
- **AppleMinOSVersion 默认 12.0**（本地 ILCompiler 10.0.11）→ target triple 为 `*-apple-macos12.0`，
  即产物要求 macOS 12+。
- **dSYM 要排除**：publish 目录里 `MufiyApp1.pdb` 有 28 MB（csproj 的 PDB 清理特意放过了它），
  macOS 上则是 `MufiyApp1.dSYM`。发布包里都排除（需要时勾 workflow 的 keep_symbols）。
- **改过 Mach-O 必须重签**：`install_name_tool -add_rpath` 之后要 `codesign --force --sign -`，
  否则 arm64 上签名失效会被内核直接杀掉。workflow 里的 rpath 兜底步骤就是这么写的。
- 包内附 `README-macos.txt`，写明未签名/未公证 → `xattr -dr com.apple.quarantine ./`。
- osx 两个 RID 的还原都已在本机验证通过；原生依赖齐全：
  `runtimes/osx/native/libSkiaSharp.dylib`、`libHarfBuzzSharp.dylib`、
